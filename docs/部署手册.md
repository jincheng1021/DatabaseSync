# 部署手册

> 适用版本：0.6.0-M6 ｜ 依据：设计方案 §12 部署与安全
> 两种部署方式：Docker 容器（推荐）与裸机 systemd。两种方式均已在交付流程中定义；容器/裸机各完成一次部署验证后交付（见验收报告）。

## 1. 系统要求

| 项 | 要求 |
| --- | --- |
| 操作系统 | Linux（x86_64/arm64）或 Windows Server |
| 容器部署 | Docker 24+ / Docker Compose v2 |
| 裸机部署 | Python 3.12+、Node.js 22+（仅构建期需要） |
| 内存 | ≥ 2 GB（全量并发 4、队列 5 万事件默认参数下） |
| 磁盘 | 系统盘外建议：数据体量 × 2（备份产物）+ 日志余量 |
| 网络 | 可达源/目标 MySQL（3306）；浏览器可达 :8080 |

## 2. Docker 部署（推荐）

### 2.1 构建与启动

```bash
cd <项目根>/deploy
docker compose up -d --build          # 构建镜像并启动
docker compose ps                     # 健康检查 healthy 即就绪
curl http://127.0.0.1:8080/api/health # {"ok":true,"version":"0.6.0-M6"}
```

国内构建机换源：

```bash
docker compose build --build-arg NPM_REGISTRY=https://registry.npmmirror.com
```

### 2.2 卷与权限

| 宿主机目录 | 容器路径 | 内容 | 权限要求 |
| --- | --- | --- | --- |
| `./data` | `/app/data` | metadata.db（SQLite WAL）+ `keys/master.key` | 容器内 uid dsync 可读写；**master.key 必须 600 且仅运行账户可读** |
| `./backups` | `/app/backups` | 备份产物（.sql.gz + SHA-256） | 读写 |
| `./logs` | `/app/logs` | 运行日志（保留 30 天自动滚动） | 读写 |

> **E4 隔离原则**：主密钥独立存于 `data/keys/`，与元数据同卷但独立子目录。**主密钥必须另行备份**——丢失后所有数据源凭据密文不可解密，需重新录入。
> 首次启动前建议：`chown -R 999:999 ./data ./backups ./logs`（镜像内 dsync 用户，**Dockerfile 已固定 uid/gid=999**，两者一致）并 `chmod 600 ./data/keys/master.key`（如已有密钥）。

### 2.3 HTTPS（反向代理）

- **1Panel 环境（推荐）**：由 1Panel「网站 → 反向代理 + 证书」承担 HTTPS，compose 中原 Caddy https profile 已移除，完整步骤见《[1Panel部署指南](1Panel部署指南.md)》；
- **非 1Panel 环境**：可继续使用 Caddy 自签证书方案——证书放置 `./certs/dsync.crt + ./certs/dsync.key`，配置参考 `deploy/Caddyfile`（留档，不在默认 compose 中）：
  ```bash
  openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
    -keyout certs/dsync.key -out certs/dsync.crt \
    -subj "/CN=dsync.internal" -addext "subjectAltName=IP:10.0.0.5"
  # 以 Caddyfile 自行编写一个 caddy 服务（reverse_proxy dsync:8080）
  ```

## 3. 裸机部署（systemd）

```bash
# 1. 目录与账户（-d 指定家目录到部署目录，避免落在无谓的 /home/dsync）
sudo useradd -r -d /opt/dsync -s /usr/sbin/nologin dsync
sudo mkdir -p /opt/dsync && sudo chown dsync:dsync /opt/dsync

# 2. 后端
cd /opt/dsync/backend
python3.12 -m venv /opt/dsync/venv
/opt/dsync/venv/bin/pip install -r requirements.txt

# 3. 前端（构建期在任意构建机执行，产物拷入）
node node_modules/vite/bin/vite.js build     # 产物 dist/ → /opt/dsync/frontend/dist

# 4. systemd 单元
sudo cp deploy/systemd/dsync.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now dsync
sudo systemctl status dsync
```

单元内置安全加固：`NoNewPrivileges` / `ProtectSystem=full` / `PrivateTmp`，写路径仅限 data/logs/backups 三目录。

## 4. 升级与回滚

使用 `deploy/upgrade.sh <version>`（容器部署）：

1. 停止容器；
2. **自动备份 SQLite**（metadata.db + WAL/SHM）到 `upgrade-backups/<时间戳>/`，并记录主密钥 SHA-256 指纹（不复制密钥本体）；
3. 导出 `binlog_position` 表到文本，作为**位点向后兼容**核验依据；
4. 构建/标记版本化镜像 `dsync:<version>` 并启动；
5. 人工核验 `/api/health` 版本号、任务详情页位点未丢失。

**回滚**：`docker tag dsync:<old> dsync:latest && docker compose up -d dsync`；如需回档数据，将备份的 `metadata.db*` 覆盖回 `./data/`。

裸机升级：git pull / 替换代码 → `pip install -r requirements.txt` → 重建前端 → `systemctl restart dsync`；升级前同样手工备份 `data/metadata.db`。

## 5. SQLite 与主密钥备份要求（E4）

- **必须**纳入常规备份：`data/metadata.db`（建议每日冷备：`sqlite3 metadata.db ".backup backup.db"`）；
- **必须**另行妥善保管：`data/keys/master.key`（600 权限）。主密钥与密文同盘同权限存放只作为运行态；备份策略上密钥应独立于 metadata.db 备份存储（如密码管理器/离线介质）；
- 主密钥丢失 = 全部数据源凭据不可解密；位点/任务配置仍可读，但数据源需重新录入。

## 6. 数据库删除后的自动初始化（删库重建）

SQLite 元数据库（`data/metadata.db`）被误删或需重置时，**服务可全自动恢复到可用状态**，无需手工建表或执行脚本：

1. **自动重建**：重启服务后，启动钩子按 `schema_migrations` 版本记录执行 v1~v4 迁移，自动重建全部 16 张表；默认运行参数（全局限流、批大小等）自动写入。日志可见「启动完成：主密钥指纹 …」即重建成功。
2. **管理员需重新引导**：管理员账号随库清空，首次访问 Web 将重新进入一次性 bootstrap（设置管理员密码）。⚠️ **bootstrap 存在安全窗口**——删库重启后任何能访问 :8080 的人都可以抢先完成初始化，共享内网环境删库重启后应**立即**完成 bootstrap。
3. **业务数据不可恢复**：数据源、任务、调度计划、运行历史、增量位点全部丢失，需重新录入与配置。`data/keys/master.key` 与库同卷不受影响，重新录入数据源密码后加解密即可正常工作。
4. **主密钥若一并丢失**：已存凭据密文不可解密，所有数据源需重新录入（见 §5）。
5. **备份铁律**：`metadata.db` 与 `keys/master.key` 必须**一并**备份，二者缺一恢复即不完整。

> 安全提示：服务默认监听 `0.0.0.0:8080`，生产环境请以防火墙/安全组限制访问来源（仅内网运维网段）；裸跑可用环境变量 `DSYNC_HOST` / `DSYNC_PORT` 调整监听地址与端口（容器部署由 compose 端口映射控制）。

## 7. 首次初始化

浏览器打开 `http://<host>:8080` → 首次访问进入管理员引导（bootstrap，一次性）→ 登录 → 录入源/目标数据源并跑预检 → 建任务。详见《用户手册》。

## 8. 部署后验证清单（冒烟）

Docker 部署完成后按序执行（全部通过即可交付）：

```bash
# 1. 服务健康（核验版本号）
curl http://127.0.0.1:8080/api/health          # {"ok":true,"version":"0.6.0-M6"}
docker compose ps                              # STATUS 应为 healthy

# 2. 首次 bootstrap（应 200；重复调用应 409 BOOTSTRAP_DONE）
curl -X POST http://127.0.0.1:8080/api/auth/bootstrap \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<强密码≥8位>"}'

# 3. 登录（应 200 并下发 dsync_session cookie）
curl -X POST http://127.0.0.1:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<同上>"}'

# 4. 前端托管（应 200 返回 index.html）
curl -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/

# 5.（可选）删库重建演练：down → 删除 ./data/metadata.db*（保留 keys/）→ up
#    预期：服务正常启动、/api/auth/status 返回 initialized:false、需重新 bootstrap
```

> 已知行为：删库/全新空库启动由装配期自动建表兜底（v0.6.0-M6 修复了空库启动崩溃），`test_db_reinit.py` 覆盖回归。
