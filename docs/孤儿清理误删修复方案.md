## 一、问题回顾

### 1.1 病灶代码（orphan_service.py:28-62）

```python
def stream(conn, schema, name):
    with conn.cursor(pymysql.cursors.SSCursor) as cur:
        cur.execute(f"SELECT `{pk}` FROM `{schema}`.`{name}` ORDER BY `{pk}`")   # ← MySQL collation 序
        ...
for tgt_pk in stream(tgt_conn, ...):
    while cur_val_src is not None and cur_val_src < tgt_pk:                      # ← Python 码点序
        cur_val_src = next(gen_src, None)
    if cur_val_src is None or cur_val_src != tgt_pk:
        batch.append(tgt_pk)                                                     # ← 误判孤儿 → DELETE
```

归并算法隐含前提「两条流按**同一个**全序排列，且 Python 的 `<`/`==` 与该序一致」——这两条在字符串主键下都不成立：

| 前提破坏点 | 说明 |
|---|---|
| 排序语言不一致 | MySQL 按列 collation 排序（标点<数字<汉字），Python 按 Unicode 码点排序（数字<汉字<全角标点） |
| 相等语义不一致 | MySQL ai_ci 下 `'abc'='ABC'`（以及 NO PAD vs PAD SPACE 的空格语义），Python 恒按字节比较 |
| 两端 collation 可能漂移 | 两库版本/建表时间不同，`ORDER BY` 可能产生**不同**序列（本事件两端一致，但结构无比对保障） |

### 1.2 实锤证据（2026-10-12 现场）

1. run 97 report_json：`orphan_deleted["lw_bzun"]=79`、`failed_tables=[]`、`rows_done=219` —— 拷贝全成功，79 行是清理删的；
2. 安全网备份 29（拷贝前目标库快照）：lw_bzun 有 219 行 —— 缺失行重刷前就存在，非「源库新增」；
3. 用备份中 219 个真实主键值复刻归并算法：**恰好误删 79 行，且与行数校验缺失集完全一致**；备份行序（InnoDB PK 序 = collation 序）≠ Python 码点序，倒位点共 5 处，全部是「（）」值；
4. run 103（新代码）确定性复现：218→139，`orphan_deleted=79`。

### 1.3 影响面

- **触发条件**：单列**字符串**主键表 + 主键值在「collation 序」与「码点序」下存在倒位（含全角/全半角混排、大小写混排、PAD 空格差异等）。int 自增主键表不受影响（数值序两序一致）；复合主键/无主键表走跳过分支不受影响。
- **波及链路**：手动/定时孤儿清理（`OrphanService.start`）与全量重刷内联清理（`full_engine._copy_one`）**共用同一个函数**，一处修复双链路生效。
- **次生缺陷**（审查报告 P1-4 其余子项，本方案一并修复）：
  - 源库被清空/替换（TRUNCATE 重灌、source_database 配错）→ 目标表可能被整体清空，无任何保险丝；
  - 主键类型两端不一致（int vs str）→ Python `<` 直接 TypeError，表失败被吞（叠加 P0-2 旧行为）；
  - 重刷内联路径对「复合主键/无主键/行过滤」跳过清理时**不登记**（手动路径有 `skipped`，内联路径没有）；
  - 清理结果只写 `orphan_deleted` 计数，删除了哪些行无记录、无抽样、无删除后复核。

## 二、修复目标与设计原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **比较语义钉死在目标端 collation** | 目标表主键唯一性、REPLACE 写入冲突判定都由目标端 collation 决定；清理的「存在性」判定必须与写入语义一致（否则会出现「刚写入的行被当孤儿删掉」）。**任何 Python 侧的字符串排序/比较都不得参与删除决策** |
| P2 | **先算账、后动手** | 先精确算出待删集合与数量，过保险丝判定，再分批删除；全过程可 dry-run 预览 |
| P3 | **误删必须有闸** | 删除量异常（比例/绝对数）、源表为空、结构指纹漂移 → 一律中止并告警，宁可漏清理不可误清理 |
| P4 | **全程可观测** | 删了几行、删了哪些（抽样）、为什么跳过、为什么拦截，全部进 report 与告警 |
| P5 | **双链路一致** | 手动/定时路径与重刷内联路径走同一实现、同一保险丝、同一登记口径 |

## 三、核心修复：SQL 侧集合差（临时表法）

### 3.1 方案选型

两库分属不同 MySQL 实例，无法跨库 JOIN，集合差必须有一侧「搬运」。候选：

| 方案 | 思路 | 正确性 | 性能 | 结论 |
|---|---|---|---|---|
| **A. 目标端临时表（推荐）** | 源端 PK 流式搬运到目标端临时表（列类型/排序规则**镜像目标 PK 列**），LEFT JOIN 求差后分批删 | ✅ 比较全部发生在目标端 MySQL 内，collation 语义天然一致；无任何 Python 排序/相等比较 | 源端一次无序全扫（**免去 ORDER BY filesort**）+ 目标端一次 JOIN + 分批删除；百万级行分钟级 | **采用** |
| B. 分批 IN 探测 | 目标端 PK 分批到源端 `WHERE pk COLLATE <目标排序规则> IN (...)`，未命中的即孤儿 | ✅ 需显式 `COLLATE` 钉死语义，且要求两端字符集兼容（否则 CONVERT） | N/5000 次往返，大表较慢 | 降级备选（目标端账号无 CREATE TEMPORARY 权限时） |
| C. 保留归并，仅改比较键 | 取两端 collation 权重做 Python 排序键 | ❌ Python 无法完整复刻 UCA 权重（版本差异、未收录字符），本质仍是猜 | — | 否决 |

### 3.2 执行流程（cleanup_orphans 重写）

```python
def cleanup_orphans(src_conn, tgt_conn, source_schema, target_schema,
                    src_table, tgt_table, pk, *,
                    guard_max_ratio=0.05, guard_min_rows=1000,
                    dry_run=False, source_fingerprint=None) -> dict:
```

1. **前置校验（任一失败 → skip，不删）**
   - 两端 PK 列类型兼容性：`information_schema.columns` 取两端 `column_type`；整型族 vs 字符串族不兼容 → skip（`reason=pk_type_mismatch`）。旧实现此处是运行期 TypeError。
   - 传入 `source_fingerprint` 时（重刷内联路径），对源表 `SHOW CREATE TABLE` 复核指纹，与开拷时不一致 → skip（`reason=source_schema_drift`，防「拷贝窗口内源表被 TRUNCATE 重建/换表」型误删）。
2. **目标端建临时表（镜像目标 PK 列，零类型漂移）**

   ```sql
   CREATE TEMPORARY TABLE `_dsync_orphan_src` AS
     SELECT `{pk}` FROM `{tgt_table}` WHERE 1=0;          -- 继承列类型/字符集/排序规则
   ALTER TABLE `_dsync_orphan_src` ADD PRIMARY KEY (`{pk}`);
   ```

3. **搬运源端 PK**：SSCursor 流式读源端 `SELECT {pk} FROM src`（**不带 ORDER BY**），每 5000 行 `INSERT IGNORE INTO _dsync_orphan_src VALUES (...)`。
   - `IGNORE` 命中（源端在自身 collation 下互异、映射到目标 collation 后重复）→ 计入 `collation_conflicts` 并写 warning：这是两端排序规则语义漂移的信号，必须暴露而不是吞掉。
4. **一次性求差集（先算账）**

   ```sql
   CREATE TEMPORARY TABLE `_dsync_orphan_del` AS
     SELECT t.`{pk}` FROM `{tgt_table}` t
     LEFT JOIN `_dsync_orphan_src` s ON t.`{pk}` = s.`{pk}`
     WHERE s.`{pk}` IS NULL;
   SELECT COUNT(*) FROM `_dsync_orphan_del`;               -- → orphan_count
   ```

5. **保险丝判定（全不命中才继续）**
   - `orphan_count == 0` → 正常返回；
   - 源表行数 = 0 且目标行数 > 0 → skip + error 告警（`reason=source_empty`，疑似源库被清空/配错库）；
   - `orphan_count > max(guard_min_rows, 目标行数 × guard_max_ratio)` → skip + warning 告警（`reason=guard_ratio`），提示走手动 dry-run 人工确认。
6. **分批删除（每批 5000，批批 commit，避免大事务）**

   ```sql
   DELETE FROM `{tgt_table}` WHERE `{pk}` IN (
     SELECT `{pk}` FROM (
       SELECT `{pk}` FROM `_dsync_orphan_del` WHERE `{pk}` > %s
       ORDER BY `{pk}` LIMIT 5000) x);                     -- 派生表物化，规避 MySQL 1093
   ```

   （此处 `ORDER BY pk` + `pk > %s` 的比较全部在 MySQL 内完成，排序规则为目标列 collation，语义正确。）
7. **删除后复核**：两端 `COUNT(*)` 对比写入 report（`orphan_after`），若仍不一致记 warning。
8. **返回结构**（替代旧 int）：

```python
{"deleted": int, "orphan_count": int, "collation_conflicts": int,
 "skipped_reason": str | None, "guard": {...} | None,
 "sample_deleted": [前 20 个被删主键], "after_check": {"source": n, "target": m}}
```

`dry_run=True` 时跳过第 6 步，返回 `orphan_count` 与待删样例，供人工确认。

### 3.3 语义说明（需写入《已知限制声明》与用户手册）

- 清理的语义仍是「**以源库当前态为准**，删除目标端多余行」——即两次清理之间源库删除的行会被同步删除，这是功能设计而非缺陷；新增保险丝防的是「源库状态异常（清空/换表/配错库）时的批量误删」。
- 存在性判定以**目标端 collation** 为准（ai_ci 下 `'abc'` 与 `'ABC'` 视为同一键，与 REPLACE 写入语义一致）。
- 复合主键/无主键/行过滤子集表（E14）仍跳过清理，但**内联路径补登记**（见 4.3）。
- 目标端账号需 `CREATE TEMPORARY TABLES` 权限；缺失时报错信息需包含权限名与降级指引（关闭任务孤儿清理开关 / 授权）。

3. 验证清单：run 明细 `orphan_deleted` 为 0（或与源端真实差集一致）、`orphan_skipped/orphan_guard` 登记正确、行数校验手动复跑 match；对含中文主键的表（lw_bzun、lw_grxx、lw_gsjs 等）各跑一次 dry-run 确认 orphan_count=0。

## 八、风险与回滚

| 风险 | 缓解 |
|---|---|
| 目标端账号缺 `CREATE TEMPORARY TABLES` | 前置探测（首次执行即暴露），报错含权限名与降级指引；临时规避=关闭任务孤儿清理开关 |
| 超大表首次上线性能 | 临时表写入为流式分批、差集为单次 JOIN、删除分批 commit；上线前先对最大表 dry-run 观察耗时 |
| 保险丝阈值过紧导致正常清理被拦 | 阈值全局可配（设置页），拦截时 report 给出 orphan_count 与样例供人工判断后走手动确认路径 |
| 临时表残留 | TEMPORARY 表会话结束自动清理，无需显式 DROP；异常中断亦同 |
| 回滚 | 单提交 git revert 即可；**回滚后旧实现仍会误删**，回滚同时必须关闭各任务孤儿清理开关（或直接不回滚、以开关规避） |
