# 全量重刷（全量从刷）功能代码审查报告

> **审查对象**：`backend/app/services/full_engine.py`（全量引擎）及其关联链路
> **关联模块**：`orphan_service.py` / `cdc_engine.py` / `cdc_transform.py` / `scheduler_service.py` / `verify_service.py` / `api/tasks.py` / 前端 `TasksView.vue`·`TaskDetailView.vue`·`ScheduleTab.vue`
> **背景**：生产部署后多次发现「某一个表的数据丢失/不一致」，本文对全量重刷功能做全面代码走读，定位缺陷、排序根因、给出修复与排查方案。
> **日期**：2026-10-12

---

## 一、结论摘要

**全量重刷功能存在缺陷，且与「单个表数据丢失」的现场表现高度相关。** 走读发现 **6 个 P0（严重）/ 4 个 P1（高）/ 6 个 P2（中）** 级问题。按与现场的关联度，最可能的根因依次是：

| 排序 | 根因 | 缺陷编号 | 与「一个表丢失」的关联 |
|---|---|---|---|
| ① | **REPLACE 先删后插在目标表唯一索引上塌缩**（219 写入 → 140 存活），且运行时零检测、列过滤校验被绕过 | **P0-4 / P1-1** | **lw_bzun 现场实锤机制**（见 §〇）：拷贝 219/219「完成」但目标仅剩 140 行 |
| ② | **表级失败被吞，整轮仍报成功**；行数校验已发现不一致却只写 report 不告警不失败 | P0-2 + P2-3 | 失败/不一致被静默，只能靠用户事后点行数校验发现 |
| ③ | **重刷不做结构迁移/比对**（目标表旧结构、索引漂移永不发现） | P0-3 | 唯一索引漂移正是 ① 的温床；源库加列则该表每次重刷必失败 |
| ④ | **重刷范围忽略映射 scope，按源库全表执行** | P0-1 | 映射外/后增的表被覆盖写入 + 孤儿清理 |
| ⑤ | **列过滤 + REPLACE：每次重刷把排除列重置为默认值** | P1-2 | 配了列过滤的表每次重刷丢列数据；若排除列恰在唯一索引里 → 直接触发 ① |
| ⑥ | 孤儿清理以源库当前态为基准的误删风险 | P1-4 | 源库该表被清空/替换后，目标表被整体清空 |

> **2026-10-12 现场复盘更新**：lw_bzun「拷贝 219/219 完成、行数校验 219 vs 140」已定位到 ①（REPLACE 唯一键塌缩），完整推理与 5 分钟定位步骤见 §〇。三个 P0 维持「需要修复」结论，另新增 P0-4 并将 P2-3 升级到第一梯队（详见 §〇.4 与 §五）。

**重要止损信息**：重刷前的「安全网备份」默认开启（`safety_net_backup=True`，`retention_tag='resync_safety_net'`，带数据），且在拷贝开始之前执行——**备份失败会整体中止重刷，不会碰数据**。如果安全网备份成功，丢失的表数据可以直接用备份恢复回滚（见 §六）。建议**第一时间确认安全网备份存在并先恢复，再排查根因**。

## 〇、现场复盘（2026-10-12 更新）：lw_bzun「拷贝 219/219 完成，行数校验 219 vs 140」

> **⚠️ 2026-10-12 深夜根因更正（实锤证据推翻本节 0.2 的「REPLACE 唯一键塌缩」推测）**：
> run 97 report_json 中 `orphan_deleted["lw_bzun"] = 79`（且 failed_tables 为空、rows_done=219），
> 目标表仅有主键 `biaozhun`、无二级唯一索引（安全网备份 DDL 为证）——REPLACE 按主键覆写不可能塌缩。
> 本节 0.3 第 1 步的判别规则本身即指向**孤儿清理误删路径**，现场证据最终落在该分支：
> `cleanup_orphans` 流式归并用 **Python 码点序（`<`/`!=`）** 比较两端按 **MySQL collation 序**
> 返回的主键流，`biaozhun` 中 5 个含全角括号「（）」的值在两种序下倒位 → 游标卡死 → 79 行被误删
> （用备份中 219 个真实主键复刻旧算法：恰好误删与缺失集完全一致的 79 行；run 103 确定性复现）。
> 目标表备份快照显示重刷**前**目标库就有全部 219 行——数据不是「源库新增未同步」，而是被工具删掉的。
> 完整机制与修复见《孤儿清理误删修复方案.md》（已实施：SQL 侧集合差 + 保险丝 + dry-run，测试 260 项全过）。
> 本节以下内容保留作排查过程记录，其中 0.2/0.4 的塌缩结论作废，P0-4 的唯一索引预检仍有效但与本事件无关。

### 0.1 现象

- 全量重刷 run 明细：`lw_bzun` **完成 219/219**（拷贝线程按批写入 219 行，无任何失败）；
- 行数校验：`lw_bzun` **源 219 / 目标 140**，缺 79 行。

### 0.2 关键推理：这不是「拷贝失败」，是「写入成功后被合并」

拷贝引擎的 `rows_done` 统计的是 **REPLACE 语句提交的行数**（`full_engine.py:972` `rows_total += len(rows)`），不是目标表最终存活行数。「写入 219 行全部成功 + 目标只剩 140 行」只有一个主流解释：

> **REPLACE INTO 的「先删后插」语义在目标表的某个唯一索引上发生了塌缩**：
> 219 行逐批 REPLACE 写入，凡是与已写入行在**目标表某个唯一索引**上冲突的行，会先 DELETE 旧行再插入新行。全部写完后，目标表存活行数 = 该唯一键的去重数 = 140。写入过程**零报错**，所以 run 明细显示 219/219 完成。
> （`_finalize` 的行数校验其实已经捕获了 219≠140，写进了 `report_json.row_count_mismatch`，但 run 仍标 success —— 即 §三 P2-3，只记录不告警不失败。）

**唯一键为什么只在目标端塌缩**（源库有唯一索引就不可能 219 行只有 140 个键值），按可能性排序：

| # | 子原因 | 机制 | 代码依据 |
|---|---|---|---|
| a | **目标表存在源库没有的唯一索引**（结构漂移：目标表是旧版本结构建的，或源库后来删了该索引） | 源库允许 219 行同键值，目标唯一索引不允许 → 互删 | 重刷**不做结构迁移、也不做结构比对**（P0-3），索引漂移永不被发现 |
| b | **唯一索引列被 column_filter 排除** | 写目标时该列不写 → 取默认值/NULL → 唯一键退化为常量 → 全表互删到 140 | **列过滤深度校验形同虚设**：`validate_mapping` 的三处 API 调用（`tasks.py:144/225/317`）**均未传 `table_meta`**，`mapping_validator.py:80-84` 中 `if cols is not None` 恒 False → 「禁止排除主键/唯一键列」的校验**从未真正执行过**（新发现，升级为 P0-4） |
| c | 多唯一索引表的普遍 REPLACE 互删（E15） | 任一唯一键冲突都删行 | 已知限制，重刷路径无提示（P1-1） |

**需要排除的备选解释（一条 SQL 即可判别）**：孤儿清理误删 79 行（源/目标 `ORDER BY` 排序规则或主键类型不一致 → 归并错位判假孤儿）。判别方法见 0.3 第 1 步。

### 0.3 现场定位步骤（按序执行，约 5 分钟）

```sql
-- 第 1 步：查重刷 run 报告，判别「塌缩」还是「清理误删」
SELECT id, state, report_json FROM run_history
WHERE task_id=<任务id> AND run_type='full_resync' ORDER BY id DESC LIMIT 3;
-- ① report_json.orphan_deleted 里 lw_bzun：
--    = 79  → 孤儿清理误删路径（查两端主键类型/排序规则）
--    = 0/无 → REPLACE 唯一键塌缩路径（继续第 2 步）
-- ② report_json.row_count_mismatch 应已有 {"table":"lw_bzun","source":219,"target":140}
-- ③ report_json.warnings 里是否出现 lw_bzun 的行过滤/列过滤提示

-- 第 2 步：比对两端表结构（重点看唯一索引）
SHOW CREATE TABLE 源库.lw_bzun;
SHOW CREATE TABLE 目标库.lw_bzun;   -- 注意 rename/前后缀映射后的表名
-- 对比每个 UNIQUE KEY：目标是否多出唯一索引？列集是否一致？含不含被排除列？

-- 第 3 步：验证塌缩假设（用目标端唯一索引列集 U）
SELECT COUNT(*) AS total, COUNT(DISTINCT <U列集>) AS distinct_uk FROM 源库.lw_bzun;
-- distinct_uk = 140 → 实锤 REPLACE 塌缩

-- 第 4 步：核对任务映射（顺带验证 P0-1/P1-2 是否相关）
SELECT mapping FROM sync_task WHERE id=<任务id>;
-- column_filter 是否含唯一索引列；row_filters 是否有 lw_bzun；scope/tables 是否含 lw_bzun

-- 第 5 步：止损——查安全网备份并评估恢复
SELECT id, created_at FROM backups
WHERE task_id=<任务id> AND retention_tag='resync_safety_net' ORDER BY id DESC LIMIT 5;
```

### 0.4 本事件对报告结论的修正

1. **P1-1（REPLACE + 多唯一索引）从「理论风险」升级为「实锤现场机制」**，并新增 **P0-4**：拷贝/重刷路径对唯一索引零检测 + 列过滤校验被绕过（见下文 P0-4）。
2. **P2-3（行数不一致只记录）必须升级到 P0 第一梯队**：本事件中 `_finalize` 已经算出了 219≠140 并写进 report，只是没失败/没告警——把 P2-3 修掉，这类事件在 run 结束瞬间就会被标记和推送，而不是靠用户事后点行数校验。
3. **P0-3 的修复范围扩展**：重刷前结构预检必须包含**索引比对**（两端唯一索引列集一致性），不能只比列名集合。
4. **P0-2 修复救不了本事件**（拷贝本身没有失败），但对「目标表不存在/缺列」类失败仍然是必需修复项。P0 三项结论均维持「需要修复」，理由见 §三。

```
start_full_resync（状态机 → full_resyncing，run_type=full_resync）
 └─ _run_resync
     ├─ 建源/目标连接，select_db（522-523）
     ├─ all_tables = 源库当前全部表；use_tables = tables or all_tables   ★ P0-1（523-524）
     ├─ 安全网备份（默认开，带数据，备份失败即中止，不碰数据）（530-544）

     ├─ _copy_tables(use_tables, replace_mode=True, orphan_cleanup=...)
     │    └─ ThreadPoolExecutor 并发 _copy_one（每表独立连接）
     │         ├─ 开拷前指纹复核（不一致 → ddl_pending 中止）（872-880）
     │         ├─ REPLACE INTO 分批写（列过滤/行过滤生效）（886-975）
     │         └─ 孤儿行 cleanup_orphans（仅单主键、无行过滤表）（992-1000）
     ├─ _finalize（自增对齐 + 行数校验 + 指纹复检）（1025-1059）
     ├─ _finish(run_id, "success")                                    ★ P0-2（561）
     └─ finally: end_resync → 后台线程重放缓存事件                    ★ P2-1（589-593）
```

**与初始化（init）的关键差异**（正是缺陷来源）：

| 环节 | init（`_run_init`） | full_resync（`_run_resync`） |
|---|---|---|
| 表范围 | `resolver.resolve(...)` **尊重映射 scope/勾选**（458 行） | `tables or all_tables` **忽略 scope，源库全表**（523-524） |
| 一致位点 P0 | 有（FTWRL/GTID 快照）（434-440 行） | **无**（直接对源库当前态覆盖，设计如此） |
| 结构迁移 | 有（`_migrate_structure` DROP+CREATE）（453 行） | **无**（只拍指纹，不迁移） |
| 失败表 | 同样只登记，但 init 有 `_finalize` 行数校验兜底显示 | 同样只登记 + 标 success |

## 三、缺陷清单

### P0-1 重刷范围忽略映射 scope：UI 承诺「映射范围内」，实际「源库全表」

**位置**：`full_engine.py:523-524`

```python
all_tables = [t["name"] for t in list_source_tables(src_conn, resolver.source_schema)]
use_tables = tables or all_tables          # ← 未调用 resolver.resolve()
```

**根因**：`MappingResolver.resolve()` 实现了 `scope=selected` 的勾选表过滤（`full_engine.py:173-181`），init 路径正确调用（458 行），但重刷路径直接用了源库全表清单。前端两个入口均传 `tables=null`，即**永远走全表分支**。

**触发条件**：任一任务（只要用户点过「全量重刷」或配了定时 full_resync 动作）。与映射怎么配无关。

**后果**（按严重度）：

1. **映射外表被覆盖 + 清理（数据丢失）**：源库存在、但不在映射 scope 内的表（用户没勾选、或 init 后新建的表），重刷时照样 `REPLACE INTO` 写入目标库，并对其执行孤儿清理。若目标库该表是**另一个任务/手动维护的数据**，会被源库版本整体覆盖、目标独有行被当孤儿删除——**这正是「某一个表的数据丢了」的最强嫌疑场景**（多任务共用一个目标库、或收窄过映射范围的部署）。
2. **映射外表在目标库不存在 → 该表 REPLACE 失败 → 表失败，但整轮仍 success**（叠加 P0-2），用户看到「重刷成功」，该表始终同步不过去。
3. 前后端语义不一致：`TasksView.vue:88` 文案「将对**映射范围内**目标表重新执行全量拷贝」、`ScheduleTab.vue:239`「默认重刷**任务映射中的**全部表」，均与后端行为不符。

**修复建议**：`use_tables = tables if tables is not None else resolver.resolve(all_tables)`，与 init/verify 口径统一；同时明确 API 语义（显式 tables = 源表名，null = 映射范围）。

### P0-2 表级失败被吞：单表拷贝失败，整轮重刷仍报「成功」

**位置**：`full_engine.py:1005-1013`（`_copy_one` 吞异常）→ `768-771`（`_copy_tables` 不抛）→ `561`（`_run_resync` 标 success）

```python
# _copy_one 的兜底：
except Exception as e:
    tp.state = "failed"; errors.append(table)      # 只登记，不上抛
# _copy_tables：
if errors: report["failed_tables"] = errors        # 不 raise
if first_escape: raise first_escape                # 仅「逃逸异常」才抛，而 _copy_one 已吞掉绝大部分
# _run_resync：
self._finish(run_id, "success", None, report, ...) # failed_tables 在 report 里，但状态是 success
```

**后果**：只要有一个表失败（目标表不存在、缺列、写入超时、连接失败……），**该表数据保持旧值或缺失，而 run_history.state=success、任务回到 idle/cdc_running、UI 显示成功**。唯一兜底是事后的自动行数校验（`verify_service.auto_row_count_after_resync`，异步、仅 row_count、不一致率 ≥0.1% 才告警），且需要用户去校验记录里看。

**与现场关联**：这解释了「多次发现有一个表不对」——每次重刷都成功、每次那个表都没刷进去。run#38 现场同款缺口（failed_tables 为空）此前修过一次（756-766 行注释），但「errors 不失败整轮」这一半一直存在。

**修复建议**：
- 终态判定：`report["failed_tables"]` 非空 → run 置 `failed`（或至少 `partial`），任务转 error 或显著告警；
- 前端任务卡片/进度页对 failed 表数量强提示（`TaskDetailView.vue:318` 已有 `failedTableCount`，但 run 成功时无告警链路）；
- `_finalize` 对 failed 表也要跑行数校验（当前 1037-1038 行跳过非 done 表）。

---

### P0-3 重刷不做结构迁移：源库结构变更后，该表每次重刷必失败

**位置**：`_run_resync` 不调用 `_migrate_structure`（对比 `_run_init:453`）；指纹在重刷开始前快照（546-548 行），开拷前只比对「快照 vs 当前」（872-880 行）——**重刷开始之前就存在的结构差异永远检测不到**。

**后果**：源库给表加了列/改了类型（哪怕是很久以前），目标表还是旧结构：

- `REPLACE INTO tgt (col_a, col_new, ...)` → 目标表无 `col_new` → **Error 1146/1054 → 表失败 → 整轮 success**（叠加 P0-2）；
- 该表此后每次重刷都失败、数据每次都是旧的——**「多次发现有一个表数据丢失」的典型形态**；
- 反之，若源库删了列，REPLACE 不写该列，目标旧数据残留（不报错，静默不一致）。

**修复建议**：重刷开拷前对每个表做一次**目标结构存在性/列集预检**（比对源表列名集合 ⊇ 目标表列名集合），缺失列/缺失表 → 明确失败并提示「需重新初始化或表重做」；或在重刷流程中增加「结构对齐」步骤（仅 ADD COLUMN 类安全 DDL 自动补，其余转 DDL 待决策）。

### P0-4（2026-10-12 新增，lw_bzun 现场直接相关）唯一索引零检测 + 列过滤校验被绕过：REPLACE 塌缩无任何运行时防护

**位置**：
- `mapping_validator.py:79-84` —— `validate_mapping` 的列过滤深度校验以 `table_meta` 为前提，而 **API 三处调用（`tasks.py:144/225/317`）均未传 `table_meta`** → 「排除列不得属于主键/唯一键」的规则**从未真正执行过**；
- `full_engine.py:860-975`（REPLACE 拷贝）+ `_run_resync` 全程无索引元数据比对；
- `precheck_service.py:115` —— `multi_unique_index` 仅数据源预检 warn，拷贝/重刷路径不引用。

**后果**：目标表存在「源库没有的唯一索引」或「含被排除列/默认值列的唯一索引」时，重刷 REPLACE 会把 219 行塌缩成 140 行——**写入零报错、run 明细 219/219 完成、行数校验才发现**。lw_bzun 现场即此形态（见 §〇）。

**修复建议**（三选一或组合，建议全做）：
1. `validate_mapping` 调用处补齐 `table_meta/target_meta`（连库取元数据，校验真正生效）；
2. `_copy_one` 开拷前（或 `_run_resync` 开拷前统一）取**两端索引元数据**比对：目标多出的唯一索引、唯一键列被排除/无源值 → **拒刷该表并明确报错**，多唯一索引 → 强 warn；
3. 行数校验不一致（`row_count_mismatch` 非空）→ run 置 failed/partial + 告警（与 P2-3 合并处理）。

### P1-1 REPLACE 语义 + 目标表多唯一索引：重刷可能误删行（E15 在重刷路径无任何提示）

**位置**：`full_engine.py:860`（`verb = "REPLACE INTO"`，init/重刷全链路统一）；`orphan_service.py:28-62`（清理）。

> **2026-10-12 更新**：本项已由「理论风险」升级为 lw_bzun 现场的直接机制之一，运行时防护缺失部分已独立为 **P0-4**（含列过滤校验被绕过的新证据）。本项保留 E15 语义说明与修复建议。

**根因**：`REPLACE INTO` 是「先删后插」：删除时按**主键 + 所有唯一键**匹配，插入时再撞唯一键又会删。目标表有 **2 个及以上唯一索引**时，一次 REPLACE 可能删掉源库语义上不该删的行（《已知限制声明》第 2 条已声明该限制）。**但 `multi_unique_index` 告警只在「数据源预检」出现（`precheck_service.py:115`），重刷路径不调用预检、无提示**。

**与现场关联**：如果「那一个表」恰好有多个唯一索引，每次重刷都可能被删掉额外行——反复出现、集中在同一张表，完全符合现场描述。

**修复建议**：`_copy_one` 开拷前检查目标表唯一索引数量 ≥2 → 记 `report["warnings"]` 并告警；对这类表降级为「先 DELETE by PK 批 + INSERT」或「ON DUPLICATE KEY UPDATE 逐列」语义（需评估与 CDC 幂等写的统一口径）。

---

### P1-2 列过滤 + REPLACE：每次重刷把「排除列」的现有值重置为默认值

**位置**：`full_engine.py:886-896`（计算 cols/write_idx）→ `943-948`（REPLACE 只写映射列）。

**根因**：`REPLACE INTO tgt (映射列) VALUES ...)` 对已存在的行是「DELETE + INSERT」，**未出现在列清单里的列一律取默认值**。`column_filter` 排除的列不在清单里 → 重刷一次，该列在目标库的存量值就被抹成 DEFAULT/NULL。

注意：配置期校验（`mapping_validator.validate_column_filter`）只禁止「NOT NULL 且无默认值」的列被排除——即**校验通过恰恰保证了「静默抹掉不报错」**。增量 CDC 链路同样只写映射列（`cdc_transform._mapped_cols`），但 CDC 只在事件到达时写；重刷是**全表 REPLACE，一次清空所有排除列**。

**与现场关联**：给「那一个表」配过列过滤（如同步时排除某业务列）的话，每次重刷都丢该列数据，且行数校验/checksum 都发现不了（校验也排除了这些列，`verify_service._compare_cols` 同样跳过 excluded）。

**修复建议**：文档明示该语义；重刷对列过滤表改用「按主键 DELETE + 带默认值占位 INSERT」不可行——正解是重刷前对排除列做**存量值保留**（先 SELECT 存量 → INSERT 时带上原值），或直接禁止对已有数据的表新增列过滤（配置期提示需重新初始化）。

---

### P1-3 分页扫描漏行：非单调主键（UUID 等）与无主键表

**位置**：`full_engine.py:800-849`（`_iter_batches`）。

- **有主键（keyset）**：`WHERE pk > last ORDER BY pk LIMIT n`。扫描窗口内插入的、**主键值小于水位线**的行永远不会被扫到（UUID、业务编码等非单调主键高发）。
- **无主键（OFFSET）**：`LIMIT n OFFSET offset`，offset 按已扫行数推进。扫描期间源库**插入**新行会导致后续窗口整体偏移 → 跳行（删除则重复读，REPLACE 幂等无害）。

**后果**：重刷完成后目标表**少量行缺失**。增量在跑的任务会被 CDC 缓存重放救回（漏扫的行有对应 INSERT 事件，重放时补写）；**`scheduled_full` 模式（无 CDC）下直到下一次重刷才可能补回**，期间表现为「表数据对不上、行数少一截」。

**修复建议**：keyset 扫描改为「快照位点 + 补扫」两段式（P0 位点处再跑一次 `pk <= 水位` 的补扫）；无主键表禁止增量写入期重刷或强制走主键补建；文档明示 UUID 主键表的重刷窗口风险。

### P1-4 孤儿清理：以源库当前态为基准，存在误删与静默失效

**位置**：`full_engine.py:992-1000`（门控）→ `orphan_service.py:28-62`（`cleanup_orphans`）。

1. **误删（最危险）**：清理逻辑是「目标有、源无 → 删」。若源库该表在拷贝之后、清理之前被清空/替换（ETL 重建表、`TRUNCATE` 后重灌、或 **`mapping.source_database` 配错指向另一个库**），目标表会被**整体清空**。主键类型在两端不一致（int vs str）时，Python `<` 比较直接 `TypeError` → 表失败（叠加 P0-2 静默成功）。
2. **拷贝失败即跳过清理**（清理在 `_copy_one` 成功路径末尾，991-1000 行）：表拷了一半失败 → 目标残留旧数据，且不清理 → 新旧混合。
3. **覆盖范围不全**：仅单列主键表清理；复合主键/无主键表跳过（`report` 无显式登记，`orphan_service.start` 手动路径有 `skipped` 登记，重刷内联路径没有）→ 源库已删行在目标长期残留。

**修复建议**：清理前对「删除行数 > 目标表行数 X%」或「源表行数=0」的情况强制二次确认/中止；补扫主键类型归一化；复合主键表实现元组归并清理；重刷路径补 `skipped` 登记。

### P1-5 CDC 重放线程与 applier 线程共享同一条 PyMySQL 连接（线程安全违规）

**位置**：`cdc_engine.py:783-845`（`_apply_batch` 无锁使用 `rt.tgt_conn`）→ `993-998`（`_apply_replay_batch` 调同一方法）。

**根因**：`end_resync` 起后台重放线程消费缓存；**同时 applier 线程仍在消费直通队列**（非重刷表的事件照常应用）。两个线程并发 `execute`/`commit` 同一条 `rt.tgt_conn`——PyMySQL 连接非线程安全，与项目自身规约（「拷贝 worker 每表独立开连接，禁止共享」）直接矛盾。后果：协议错乱（Packet sequence 错）、批提交互相交错、事件丢失或 `_TargetWriteFailed` → 任务转 ERROR。

**修复建议**：重放期间 applier 暂停消费（或重放走独立连接 + 串行化），并给 `_apply_batch` 的连接使用加锁。

---

### P2-1 重刷「成功」先于缓存重放完成，存在停止竞态窗口

**位置**：`full_engine.py:561`（`_finish(success)`）→ `587-593`（finally 才 `end_resync` 起异步重放线程）。

run 标记成功、任务迁回 idle/cdc_running 时，重刷窗口内缓存的事件**尚未重放**。此时用户点「停止增量」：`stop()` 只 `join(timeout=15s)` 重放线程，超时后 `_close_target` 关连接 → 重放失败 → 任务 ERROR（有告警，不静默，但用户体验是一次「成功后的失败」）。UI 有 `caching/replaying` 展示（`TaskDetailView.vue:504`），但无「重放未完成禁止停止」的强约束。

**修复建议**：`end_resync` 同步等待（或轮询 `replaying` 置位）后再 `_finish(success)`；停止入口对 replaying 状态做软拦截。

---

### P2-2 CDC 未运行时的重刷：事件既不缓存也不重放

**位置**：`full_engine.py:550-551` → `cdc_engine.py:858-861`（`rt` 不存在直接 return）。

`init_plus_cdc` 任务在 IDLE（增量未启动）或 `scheduled_full` 模式下重刷：`begin_resync` 找不到 runtime 静默返回 → 重刷期间源库变更**无捕获**。IDLE 任务后续启动 CDC 会从 P0 位点重放，可自愈（幂等）；但若 P0 之前的 binlog 已被源库清理 → `needs_reinit`。`scheduled_full` 无 CDC，窗口内更新丢失/删除残留直到下次重刷。

**修复建议**：`begin_resync` 对「任务模式应跑 CDC 但未运行」的情况记 `report["warnings"]`；或重刷前强制要求 CDC 运行（init_plus_cdc）。

---

### P2-3 `_finalize` 行数不一致只记录、不失败

**位置**：`full_engine.py:1048-1052`。`row_count_mismatch` 进 report，run 仍 success。仅靠异步自动行数校验兜底（且只查行数，不查内容）。

**修复建议**：`row_count_mismatch` 非空 → run 置 failed/partial 并告警（与 P0-2 合并处理）。

### P2-4 结构迁移「先 DROP 后 CREATE」：CREATE 失败 → 目标表丢失

**位置**：`full_engine.py:645-649`（`_migrate_structure`，init 与表重做共用）。与视图/存储过程不同（668、685 行有 try 跳过登记），表的 `DROP TABLE IF EXISTS` + `CREATE` **没有 per-table 容错**：CREATE 抛错（definer 权限、字符集、不支持语法）→ 异常上抛 → 整 run failed，**但表已经被 DROP 了** → 目标表消失，需人工重建。`_run_table_redo`（DDL 决策后重做受影响表）同路径。

**修复建议**：CREATE 失败时把「已 DROP 未建成」的表登记到 report 并尝试用原始 DDL 重试/转人工；或改为「CREATE 新临时表 → RENAME」两步（失败可回退）。

### P2-5 断点续传实际不可用：checkpoint 仅在暂停时落库

**位置**：`full_engine.py:773-780`（`_wait_if_paused` 内才写 checkpoint）、`904-913`（内存 `resume_ckpt`）。进程崩溃/被杀 → 内存位点丢失 → 重跑只能从头全表扫（安全但低效；大表重刷中断代价高）。每批落库的只有 `rows_done`（975 行）。

**修复建议**：按批（或每 N 秒）持久化 `last_pk/offset`，崩溃后从 `get_table_checkpoint` 续扫。

## 四、「一个表数据丢失」根因排查路线

按可能性从高到低，每条附诊断方法（SQLite 元数据库 = 工具自带库；源/目标库按任务映射）：

**第 0 步（止损）**：确认安全网备份并评估恢复。

```sql
SELECT id, created_at, retention_tag, datasource_id FROM backups
WHERE task_id = ? AND retention_tag = 'resync_safety_net' ORDER BY id DESC LIMIT 5;
```

**第 1 步：看重刷 run 的真实结果（验证 P0-2/P0-3）**

```sql
SELECT id, state, error_summary, report_json FROM run_history
WHERE task_id = ? AND run_type = 'full_resync' ORDER BY id DESC LIMIT 5;
-- 重点看 report_json.failed_tables / row_count_mismatch / orphan_deleted / warnings
SELECT table_name, state, rows_total, rows_done, error FROM run_table_detail
WHERE run_id = <上面的 run id>;
```

若「那一个表」在 `failed_tables` 里 → 根因 ①/③，看 `error` 列内容：
- `Unknown column 'xxx'` / `Table 'db.tbl' doesn't exist` → **P0-3（源库加列/目标缺表）**；
- 超时/断连类 → 查看是否每次必现。

**第 2 步：比对源/目标结构（验证 P0-3）**

```sql
SHOW CREATE TABLE `源库`.`那张表`;   -- 源库执行
SHOW CREATE TABLE `目标库`.`那张表`; -- 目标库执行（注意 rename/前后缀映射后的名字）
```
源表有、目标表没有的列 → 每次重刷必失败。同时看目标表是否真的存在。

**第 3 步：核对任务映射（验证 P0-1 / P1-2）**

```sql
SELECT mapping FROM sync_task WHERE id = ?;
```
- `scope=selected` 且 `tables` 不含该表，或 `source_database` 与预期不符 → **P0-1**：重刷把映射外表也覆盖+清理了；若该表在目标库原本有独立数据 → 被覆盖/清空。
- `column_filter` 含该表 → **P1-2**：重刷把排除列抹成默认值（对比备份前后该列值可确认）。

**第 4 步：检查目标表唯一索引（验证 P1-1）**

```sql
SHOW INDEX FROM `目标库`.`那张表`;   -- 非主键的唯一索引 ≥ 1 个即中招
```

**第 5 步：核对主键形态与写入时序（验证 P1-3）**

- 主键是 UUID/业务编码（非单调递增）→ keyset 漏行；
- 无主键 → OFFSET 跳行；
- 结合 `run_table_detail.rows_done` 与源表 `SELECT COUNT(*)` 的差，以及重刷窗口内的源库写入量判断。

**第 6 步：孤儿清理量（验证 P1-4）**

`report_json.orphan_deleted["那张表"]` 数值异常大（接近目标表行数）→ 源库在该窗口被清空/替换，或 source_database 指错。

**第 7 步：行级 diff 定位缺失/差异行**

用工具自带「数据校验」（checksum + 行级 diff）对那张表跑一次，`target_missing` / `target_extra` / `mismatch` 的分布可直接区分上述根因。

## 六、止损与恢复（安全网备份）

1. 每次重刷前（默认开启、带数据）会对**目标库涉及表**做备份，`retention_tag='resync_safety_net'`，且在拷贝开始**之前**执行——备份失败则重刷整体中止，不碰数据。
2. 若丢失表的数据在备份时间点之后又发生过合法变更，恢复备份会一并回退这些变更，需与业务确认窗口。
3. 恢复走「备份恢复」功能（仅支持本工具产物）。若安全网被手动关闭（`safety_net_backup=False`）或备份已过期，只能按 §四 定位根因后重新初始化/重刷修复。

| **P0-4** 唯一索引零检测 + 列过滤校验被绕过 | 双层修复：a) 预检唯一索引比对——目标独有唯一键（源库无同列集唯一约束，含主键蕴含判定）或唯一键含被列过滤排除的列 → **拒刷**（直接拦截 lw_bzun 塌缩机制）；b) API 三处 `validate_mapping` 补传连库列元数据（`_live_schema_columns` 单条聚合查询，失败降级为警告不阻塞保存），「排除列不得属于主键/唯一键」规则首次真正生效 | `full_engine.py`；`api/tasks.py`（create/update/batch 三处） |

**安全判定口径**（预检第 ④ 项）：源库任一唯一约束（含主键）列集 ⊆ 目标唯一键列集 → 判定不塌缩、放行；否则拒刷。目标联合唯一 `(id, code)` 且源主键为 `(id)` 时放行，目标独有 `uk(code)` 时拒刷。

**运行时行为变化提示**：
1. 重刷/初始化/表重做的 run 终态新增 `partial`（执行历史显示「完成（有差异）」），筛选与统计按非 success 处理；
2. 结构不齐的表会被**显式拒刷**并给出对齐指引（此前是静默塌缩或静默失败）——这是预期行为变更，现场需对齐两端结构后重试；
3. 任务保存时若配置了列过滤，会连库取列元数据做深度校验（连接失败降级为 `mapping_warnings` 提示，运行时预检兜底）。
